# Testing this extension

This directory holds the tests for the extension:

- `sql/`: [SQLLogicTests](https://duckdb.org/dev/sqllogictest/intro.html) that exercise every SQL function through DuckDB.
- `cpp/` and `fuzz/`: standalone C++ checks and fuzz targets for the parsers, grid math and missing-value handling. They
  need no DuckDB build; see "Robustness and fuzzing" below.
- `herbie_compare/`: a Python suite that compares results with Herbie and ecCodes (see its own README).
- `data/`: test data and the scripts that generate it (see "Test data" below).

The root makefile contains targets to build and run all of these tests. To run the SQLLogicTests:
```bash
make test
```
or 
```bash
make test_debug
```

## Test data

- `test/data/sample.grib2`: a 277-byte synthetic GRIB2 message (16 x 31 grid, complex packing with spatial differencing). Regenerate it with `test/data/generate_sample.py` (needs `pip install eccodes ecmwflibs`).
- `fixtures/nbm_msg.grib2`: a real NBM CONUS message. See `fixtures/README.md` for its provenance.
- `test/data/multi.grib2`: four messages (Guam, Puerto Rico, Hawaii, `sample.grib2`) on three different grids, with `test/data/multi.grib2.idx`, a **synthetic** wgrib2-style inventory built from ecCodes keys for testing the sidecar code path.
- `test/data/masked_gu.grib2`: the Guam message with a bitmap masking 400 cells, generated by `generate_masked_sample.py`. Unmasked values are re-quantized by ecCodes when it re-encodes, so expected values come from reading this file back, not from the original.
- `test/data/missing_complex.grib2`, `missing_spatial.grib2` and `real_9999.grib2`: the Guam message re-encoded so the same 400 cells have no data in three different ways, generated by `generate_missing_value_samples.py`: flagged by template 5.2 or 5.3 packing with no bitmap, and masked by a bitmap among real values of exactly 9999. `test/cpp/missing_value_check.cpp` checks them against ecCodes directly. Values are re-quantized by ecCodes, so expected values come from reading the files back.
- `test/data/simple_window.grib2`, `simple_bitmap.grib2` and `simple_9999.grib2`: a 120 x 100 window of the real HRRR snow-depth grid (around Mount Rainier) re-encoded with template 5.0, generated by `generate_simple_packed_samples.py`. They are synthetic re-encodings of real values on a real grid, not messages NOAA produced. No bitmap; a bitmap masking 300 cells; and a bitmap with integers of which 1064 are exactly 9999 (the missing-value marker's default). `test/cpp/missing_value_check.cpp` checks them against ecCodes directly.
- `fixtures/hrrr_msg*.grib2`: three real HRRR messages (packing 5.0 and 5.3, Lambert, earth shape 6). See `fixtures/README.md`. They are in the screen, robustness, missing-value and SQL tests, and the HRRR grid is a section of `test/data/grid_reference.txt`.
- `fixtures/nbm_complex_msg.grib2`: a real NBM message using packing template 5.2. See `fixtures/README.md`.
- `test/data/interval_steps.grib2` and `.idx`: four tiny HRRR messages with a **synthetic** inventory that labels them `0-6 hour acc fcst`, `6-12 hour max fcst`, `1-2 hour missing fcst` and `15 min fcst`, for testing how `valid_time` and `step_hours` are derived from interval fields. Generated by `generate_interval_sample.py` (pure Python).
- `test/data/stale.grib2` and `stale.grib2.idx`: two copies of `sample.grib2` with an `.idx` whose offsets do not match the file, for the "does this .idx belong to the file?" check.
- `test/data/bad_bitmap_indicator.grib2`: the smallest real HRRR message with its bitmap indicator changed from 255 (no bitmap) to 254 (reuse a previous bitmap), generated by `generate_bad_bitmap_indicator_sample.py` (pure Python). ecCodes would decode it as if it had no bitmap, so the extension must refuse it.
- `test/data/degenerate_polar.grib2`: a 20 x 20 north polar stereographic message with LaD = -90 degrees (projection scale zero), generated by `generate_degenerate_polar_sample.py` (needs `pip install eccodes numpy`). The grid must be refused.
- `test/data/nbm_idx_expected.tsv`, `test/data/sections_reference.tsv`, `test/data/packing_templates.tsv`, `test/data/grid_reference.txt`: reference data for the standalone C++ checks, generated by `generate_message_reference.py` and `generate_grid_reference.py` (both need `pip install eccodes ecmwflibs`).

Tests use paths relative to the repository root, so run them from there.

## Running tests

`make test` needs Python 3.10 or newer (it calls DuckDB's `run_tests.py`). Otherwise run the binary directly:
```bash
./build/release/test/unittest "test/*"
```

## Robustness and fuzzing

`test/cpp/robustness_check.cpp` throws truncated, bit-flipped and random input at the `.idx` parser, the section-header
parser and the grid validation, and is meant to be built with the sanitizers so any memory error fails the run:

```bash
g++ -std=c++17 -O1 -g -fsanitize=address,undefined -fno-sanitize-recover=all -I src/include \
    test/cpp/robustness_check.cpp -o /tmp/robustness_check && /tmp/robustness_check
```

`test/fuzz/` holds libFuzzer targets for the same two parsers (build lines are in each file). CI runs both: the
robustness check on every push, and a 45-second fuzz run of each parser.

The robustness check also holds regression tests for bugs found in review: a message length of 2^63 or more that sent the
no-`.idx` walk backwards forever, an `.idx` forecast step large enough to overflow `valid_time`, and point counts large
enough to size a huge allocation. Each one was confirmed to fail with its fix removed.

`test/cpp/eccodes_threads_check.cpp` decodes six messages from eight threads through `Grib2EccodesGuard`
(`src/include/grib2_threading.hpp`) and checks every result against a single-threaded decode. CI builds it against
Ubuntu's ecCodes, which is not built thread-safe, so it exercises the serialising path. It cannot prove that the guard
is needed: a race may not show on a small runner. `--unguarded` runs the same work without the guard, as an experiment.

These cover the parsers in this repository only. ecCodes itself, which decodes every message, is not fuzzed here; see
"Untrusted input" in the README.

## Remote reads

`test/remote_read/` runs the built DuckDB CLI with httpfs against `range_server.py`, a small local server with `HEAD`,
`Range` and a request log, which also stands in for an S3 bucket in path style. It checks that a remote read returns what
a local read does, that only the selected message is fetched when an `.idx` is present, that a missing `.idx` is handled
when the server answers 404 or S3's 403 (and that a 401 is still an error), that `grib2_io_threads > 1` gives the same
rows, and that a truncated or missing remote file is an error. Standard library only; needs `make` and, on first use,
network access to install httpfs (or `GRIB2_HTTPFS`). It runs in the manual Herbie workflow.

    python3 -m unittest discover -s test/remote_read -v
