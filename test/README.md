# Testing this extension
This directory contains all the tests for this extension. The `sql` directory holds tests that are written as [SQLLogicTests](https://duckdb.org/dev/sqllogictest/intro.html). DuckDB aims to have most its tests in this format as SQL statements, so for the grib2 extension, this should probably be the goal too.

The root makefile contains targets to build and run all of these tests. To run the SQLLogicTests:
```bash
make test
```
or 
```bash
make test_debug
```

## Test data

- `test/data/sample.grib2`: a 277-byte synthetic GRIB2 message (16 x 31 grid, complex packing with spatial differencing). Regenerate it with `test/data/generate_sample.py` (needs `pip install eccodes ecmwflibs`).
- `fixtures/nbm_msg.grib2`: a real NBM CONUS message. See `fixtures/README.md` for its provenance.
- `test/data/multi.grib2`: four messages (Guam, Puerto Rico, Hawaii, `sample.grib2`) on three different grids, with `test/data/multi.grib2.idx`, a **synthetic** wgrib2-style inventory built from ecCodes keys for testing the sidecar code path.
- `test/data/masked_gu.grib2`: the Guam message with a bitmap masking 400 cells, generated by `generate_masked_sample.py`. Unmasked values are re-quantized by ecCodes when it re-encodes, so expected values come from reading this file back, not from the original.
- `fixtures/nbm_complex_msg.grib2`: a real NBM message using packing template 5.2. See `fixtures/README.md`.
- `test/data/stale.grib2` and `stale.grib2.idx`: two copies of `sample.grib2` with an `.idx` whose offsets do not match the file, for the "does this .idx belong to the file?" check.
- `test/data/nbm_idx_expected.tsv`, `test/data/sections_reference.tsv`, `test/data/packing_templates.tsv`, `test/data/grid_reference.txt`: reference data for the standalone C++ checks, generated by `generate_message_reference.py` and `generate_grid_reference.py` (both need `pip install eccodes ecmwflibs`).

Tests use paths relative to the repository root, so run them from there.

## Running tests

`make test` needs Python 3.10 or newer (it calls DuckDB's `run_tests.py`). Otherwise run the binary directly:
```bash
./build/release/test/unittest "test/*"
```

## Robustness and fuzzing

`test/cpp/robustness_check.cpp` throws truncated, bit-flipped and random input at the `.idx` parser, the section-header
parser and the grid validation, and is meant to be built with the sanitizers so any memory error fails the run:

```bash
g++ -std=c++17 -O1 -g -fsanitize=address,undefined -fno-sanitize-recover=all -I src/include \
    test/cpp/robustness_check.cpp -o /tmp/robustness_check && /tmp/robustness_check
```

`test/fuzz/` holds libFuzzer targets for the same two parsers (build lines are in each file). CI runs both: the
robustness check on every push, and a 45-second fuzz run of each parser.

The robustness check also holds regression tests for bugs found in review: a message length of 2^63 or more that sent the
no-`.idx` walk backwards forever, an `.idx` forecast step large enough to overflow `valid_time`, and point counts large
enough to size a huge allocation. Each one was confirmed to fail with its fix removed.

These cover the parsers in this repository only. ecCodes itself, which decodes every message, is not fuzzed here; see
"Untrusted input" in the README.
